# 从零实现一棵 C++ 对象树：关系、所有权与生命周期观察

> 本文记录了一次受 Qt `QObject` 启发的对象树学习过程。
>
> 重点不在复刻 Qt 的全部实现，而在于通过五个逐步演进的版本，理解对象关系、内存所有权和生命周期观察为什么必须被区分。

## 1. 为什么需要对象树？

GUI、场景对象和文档模型天然具有层级关系：

```text
Window
├── Toolbar
│   └── Button
└── View
    ├── Camera
    └── Selection
```

如果这些关系只有业务含义，没有生命周期含义，那么销毁一个 `Window` 时，调用者必须手动记住所有清理步骤：

```cpp
delete button;
delete toolbar;
delete camera;
delete selection;
delete view;
delete window;
```

随着对象数量增加，并开始支持提前删除、动态换父和跨作用域引用，很快就会遇到：

- 忘记释放对象，造成内存泄漏；
- 多处都认为自己是所有者，造成重复释放；
- 父对象仍保存已经死亡的子对象；
- 外部保存的裸指针变成悬空指针；
- 信号槽继续调用已经销毁的接收者。

对象树的价值，不只是让对象排成一棵树，而是建立一套统一的生命周期规则：

```text
父对象拥有子对象
→ 父对象死亡时，整棵子树自动销毁
→ 子对象提前死亡时，自动脱离父对象
```

它将原本散落在业务代码中的手动清理，收束为一个确定性的生命周期协议。

Qt 的 `QObject` 对象树也是类似的思路：对象加入父对象的 `children()` 列表后，由父对象负责在析构时销毁它。子对象提前析构时，也会自动从父对象中移除。

参考资料：

- [Qt Object Trees & Ownership](https://doc.qt.io/qt-6/objecttrees.html)
- [QObject 文档](https://doc.qt.io/qt-6/qobject.html)

## 2. Version 1：先让级联销毁跑起来

第一版采用最直观的结构：

```cpp
class Object
{
private:
    std::unordered_set<Object*> m_Children;
    Object* m_Parent = nullptr;
};
```

这里约定：

- `m_Parent` 是非拥有指针；
- `m_Children` 中的指针由当前对象负责释放；
- 父对象析构时递归删除 children；
- 子对象析构时从 parent 中移除自己。

最初的析构思路类似：

```cpp
~Object()
{
    if (m_Parent)
    {
        m_Parent->RemoveChild(this);
    }

    for (auto* child : m_Children)
    {
        delete child;
    }
}
```

### 2.1 第一个问题：析构本身会修改树

父对象正在遍历 `m_Children` 时：

```cpp
delete child;
```

会进入子对象的析构函数。子对象又会调用：

```cpp
m_Parent->RemoveChild(this);
```

于是发生：

```text
父对象正在遍历 children
→ 子对象析构
→ 子对象修改同一个 children
→ 父对象迭代器失效
→ 未定义行为
```

这让我第一次意识到：

> 销毁一个对象不只是释放内存，它同时也是一次对象树结构修改。

解决方案不是复杂的延迟标记，而是先解除结构关系，再销毁对象：

```cpp
while (!m_Children.empty())
{
    auto iter = m_Children.begin();
    Object* child = *iter;

    m_Children.erase(iter);
    child->m_Parent = nullptr;

    delete child;
}
```

每一轮都重新获取 `begin()`，不会递增已经失效的迭代器；同时，子对象析构时看到的 `m_Parent` 已经为空，也不会回头修改父容器。

这一版得到了一条贯穿后续设计的重要原则：

> 先解除关系，再销毁对象。

## 3. Version 2：对象树不能只会销毁，还要允许变化

真实的对象树不会在构造完成后永远保持不变。

例如：

```text
按钮从一个面板移动到另一个面板
场景节点重新挂载
文档节点被拖入另一个分组
```

因此第二版加入了 `SetParent()`：

```cpp
child->SetParent(newParent);
```

一次换父操作至少包含：

```text
从旧父对象移除
→ 修改 child.parent
→ 加入新父对象
```

### 3.1 第二个问题：双向关系很容易只改一半

为了提供不同使用方式，我一度同时维护了：

```cpp
child->SetParent(parent);
parent->AddChild(child);
```

如果两个公开接口都独立实现完整换父逻辑，很容易出现不一致：

```text
SetParent 修改了 child.parent
但旧 parent.children 没有移除
```

或者：

```text
AddChild 修改了 parent.children
但 child.parent 没有更新
```

还曾出现过一个典型错误：换父时从新父对象中移除 child，而不是从旧父对象中移除。

最终结果可能变成：

```text
旧父对象认为自己仍然拥有 child
新父对象也认为自己拥有 child
→ 两个父对象最终重复 delete
```

这说明对象树不能只依赖“每个接口尽量写对”，而必须建立不可被绕过的结构不变量。

### 3.2 为什么要禁止复制？

如果允许编译器自动复制：

```cpp
Object copy = original;
```

那么 `m_Parent` 和 `m_Children` 中的指针也会被复制。

两个不同的 Object 随后可能同时声称拥有同一批子对象。

因此 Object 更接近“身份”，而不是普通“值”：

```cpp
Object(const Object&) = delete;
Object& operator=(const Object&) = delete;
```

同时，Object 将作为派生对象的公共生命周期基类，所以析构函数也应是虚函数：

```cpp
virtual ~Object() = default;
```

## 4. Version 3：从功能代码升级为不变量设计

第三版确定了唯一的高层事务入口：

```cpp
void SetParent(Object* newParent);
```

底层只保留私有结构操作：

```cpp
void AttachChild(Object* child);
void DetachChild(Object* child);
```

### 4.1 为什么要区分高层事务和底层原语？

如果：

```text
SetParent → AddChild
AddChild  → SetParent
```

两个接口会互相递归。

更深层的问题是，两个接口都试图负责整个事务。

最终形成的层次是：

```text
SetParent
├── 检查新关系是否合法
├── 调用旧父对象的 DetachChild
├── 调用新父对象的 AttachChild
└── 更新 m_Parent

AttachChild / DetachChild
└── 只执行单侧底层容器修改
```

简化后的核心代码类似：

```cpp
void SetParent(Object* newParent)
{
    if (m_Parent == newParent)
    {
        return;
    }

    for (Object* ancestor = newParent;
         ancestor;
         ancestor = ancestor->GetParent())
    {
        if (ancestor == this)
        {
            throw std::logic_error(
                "An object cannot become a child of itself or its descendant");
        }
    }

    Object* oldParent = m_Parent;

    if (newParent)
    {
        newParent->AttachChild(this);
    }

    if (oldParent)
    {
        oldParent->DetachChild(this);
    }

    m_Parent = newParent;
}
```

### 4.2 对象树需要维护哪些不变量？

从这一版开始，我不再只关注某个函数是否能运行，而是关注整个对象树在任意公开操作后必须满足的条件。

最核心的不变量是：

```text
child.parent == parent
当且仅当
parent.children 中包含 child
```

此外还有：

- 一个对象最多只有一个父对象；
- 对象不能成为自己的父对象；
- 对象不能把自己的后代设置为父对象；
- 对象树中不能出现环；
- 重复设置相同父对象是无副作用操作；
- `SetParent(nullptr)` 可以让对象脱离当前树。

### 4.3 栈对象暴露了裸指针模型的边界

裸指针无法告诉我们：

```text
这个地址来自 new？
来自栈？
是另一个对象的成员？
还是静态对象？
```

下面的构造顺序通常安全：

```cpp
Object parent("parent");
Object child("child", &parent);
```

离开作用域时按构造的逆序析构，child 会先脱离 parent。

但下面的顺序存在危险：

```cpp
Object child("child");
Object parent("parent");

child.SetParent(&parent);
```

parent 会先析构，并尝试删除栈上的 child。

这不是增加一个简单判断就能解决的问题，而是裸指针模型的能力边界：

> 裸指针对象树允许灵活的运行期关系，但必须附带生命周期使用契约。

### 4.4 Version 3 的定位

Version 3 最终形成了一个接近 QObject 风格的模型：

```text
裸指针表达关系
Object 的析构协议表达所有权
```

它的优点是 API 简单，换父自然；代价是所有权主要存在于协议和不变量中，而不是直接编码在指针类型里。

## 5. Version 4：用 unique_ptr 重新追问“谁拥有对象”

因为平时更习惯智能指针，我又设计了一版严格所有权树：

```cpp
class Object
{
private:
    Object* m_Parent = nullptr;

    std::unordered_map<
        Object*,
        std::unique_ptr<Object>
    > m_Children;
};
```

其中：

```text
m_Parent
    是非拥有观察指针

m_Children 中的 unique_ptr
    明确表达当前对象对子对象的唯一所有权
```

### 5.1 为什么要尝试 unique_ptr？

Version 3 中：

```cpp
std::unordered_set<Object*> m_Children;
```

从类型上看不出这些指针究竟是拥有关系还是观察关系。

`unique_ptr` 可以把规则写进类型系统：

```text
谁持有 unique_ptr，谁就是唯一所有者
```

它也能阻止调用者在正常 API 下把普通栈地址直接交给父对象拥有。

### 5.2 第三个问题：SetParent 无法隐藏所有权转移

裸指针版换父只是修改关系：

```cpp
child->SetParent(newParent);
```

智能指针版换父则必须真正移动所有权：

```text
旧父对象交出 unique_ptr
→ 临时所有者接住
→ 新父对象接收 unique_ptr
```

对象无法仅凭 `this` 找到外部那个拥有自己的 `unique_ptr`。

因此 Version 4 的 API 自然变成：

```cpp
Object* AttachChild(std::unique_ptr<Object> child);

std::unique_ptr<Object> DetachChild(Object* child);

void Reparent(Object* newParent);
```

换父操作看起来比 Version 3 更“别扭”，但这不是实现失败，而是一个重要结论：

> 一旦所有权进入类型系统，所有权转移也必须在 API 中显式出现。

### 5.3 views 不是容器快照

智能指针版的析构过程中，我曾尝试遍历：

```cpp
m_Children | std::views::keys
```

并在循环中擦除当前元素。

但 range view 不是快照，它仍然惰性地使用原容器的迭代器，因此再次出现迭代器失效。

最终采用两阶段处理：

```cpp
for (auto* child : m_Children | std::views::keys)
{
    child->m_Parent = nullptr;
}

m_Children.clear();
```

第一阶段只解除关系，不修改容器；第二阶段统一释放所有 `unique_ptr`。

这与 Version 1 得到的是同一条经验：

```text
先解除结构
再释放所有权
```

### 5.4 Version 3 和 Version 4 谁更好？

它们不是简单的先进与落后关系，而是两种不同取舍：

| 模型 | 优势 | 代价 |
|---|---|---|
| Version 3：裸指针对象树 | API 简洁，换父自然，接近 QObject | 所有权主要依靠协议 |
| Version 4：unique_ptr 对象树 | 所有权由类型系统明确保证 | 所有权转移接口更显式、更复杂 |

这次实验让我认识到：

> 现代 C++ 并不意味着所有位置都必须使用智能指针。选择哪种指针，取决于需要表达的是所有权、观察关系，还是短期借用。

## 6. Version 5：所有权安全不等于访问安全

Version 4 已经保证：

- 子对象不会泄漏；
- 父对象不会重复释放同一个 child；
- 换父时会显式转移唯一所有权。

但测试代码仍然需要保存：

```cpp
Object* rawObject = owner.get();
```

这些指针不拥有对象，却可能被函数、类成员或其他模块长期保存。

一旦某个子树被销毁：

```text
unique_ptr 正确释放对象
但外部 Object* 仍保存旧地址
→ 所有权完全正确
→ 访问仍然可能产生 UB
```

这让我意识到：

> 所有权和观察是两个不同的问题。

`unique_ptr` 回答：

```text
谁负责删除对象？
```

观察指针回答：

```text
我不负责删除，但我如何知道对象是否仍然活着？
```

### 6.1 LifetimeToken：对象身份不能只靠地址

仅检查裸指针是否为空没有意义，因为对象死亡时，外部裸指针不会自动变空。

而且，同一块内存以后可能被另一个新对象复用。地址相同，并不代表还是原来的对象。

因此，每个 Object 构造时创建一个独立的生命周期令牌：

```cpp
class LifetimeToken
{
};

class Object
{
private:
    std::shared_ptr<LifetimeToken> m_LifetimeToken;
};
```

对象析构开始时释放令牌：

```cpp
Object::~Object()
{
    m_LifetimeToken.reset();

    // 随后再处理 children。
}
```

### 6.2 ObjectPtr：只观察，不拥有

观察指针保存：

```cpp
template<class T>
class ObjectPtr
{
private:
    T* m_Pointer = nullptr;
    std::weak_ptr<LifetimeToken> m_LifetimeToken;
};
```

读取时先检查令牌：

```cpp
[[nodiscard]]
T* Get() const noexcept
{
    if (m_LifetimeToken.expired())
    {
        return nullptr;
    }

    return m_Pointer;
}
```

其语义是：

```text
LifetimeToken 还活着
→ Object 仍然存在
→ 返回原始地址

LifetimeToken 已过期
→ Object 已进入析构
→ 返回 nullptr
```

即使以后有新对象复用了相同地址，新对象也拥有另一枚 LifetimeToken，因此旧 ObjectPtr 不会“复活”。

这种设计与 Qt 的 `QPointer` 目标相似：它不拥有 `QObject`，但会在被观察对象死亡后变为空。

参考：[QPointer 文档](https://doc.qt.io/qt-6/qpointer.html)

### 6.3 三种指针语义终于被区分

到这里，可以明确区分三种用途：

```cpp
std::unique_ptr<Object> owner;
// 明确拥有对象，负责销毁。

Object* borrowed;
// 短期借用，例如函数参数。

ObjectPtr<Object> observer;
// 长期观察对象，但不负责销毁。
```

这也是整个对象树学习中最重要的抽象结果：

```text
关系：
    parent / children 描述对象位于哪里

所有权：
    裸指针协议或 unique_ptr 描述谁负责销毁

观察：
    ObjectPtr 描述如何安全保存非拥有引用
```

## 7. 贯穿五个版本的设计经验

### 7.1 对象树不是垃圾回收

对象树是一种确定性的层级所有权：

```text
删除根节点
→ 同步、递归地删除整棵子树
```

它不会自动寻找所有不可达对象，也不是通用 GC。

### 7.2 双向关系必须有唯一事务入口

只要 parent 和 children 同时保存关系，就必须集中维护不变量。

不能让多个公开接口各自维护一套近似但不完全一致的逻辑。

### 7.3 析构前先解除关系

无论裸指针还是智能指针：

```text
先从结构中解除
→ 再销毁对象
```

否则子对象析构可能重入并修改父容器。

### 7.4 所有权模型决定 API 形状

裸指针模型适合：

```cpp
child->SetParent(parent);
```

`unique_ptr` 模型适合：

```cpp
auto child = oldParent.DetachChild(pointer);
newParent.AttachChild(std::move(child));
```

API 的“别扭”有时是在提醒我们：底层语义已经从修改关系，变成了转移所有权。

### 7.5 智能指针不能消除所有悬空引用

只要系统允许非拥有访问，就仍然需要：

- 明确的短期借用；
- 生命周期观察器；
- 或共享所有权。

`ObjectPtr` 不是所有者，而是一枚身份探针。

### 7.6 单线程安全不等于并发安全

当前 ObjectPtr 可以判断对象是否已经死亡：

```cpp
if (observer)
{
    observer->DoSomething();
}
```

但在多线程环境中，对象仍可能在检查之后、调用之前被另一个线程销毁。

因此当前模型的合理边界是单线程对象系统。

如果允许跨线程并发销毁，还需要：

- 外部互斥；
- 线程归属约束；
- 或可以提升为强引用的共享所有权。

## 8. 为什么下一步适合融合信号槽？

对象树现在已经可以回答：

- 谁拥有对象；
- 子树如何级联销毁；
- 对象何时进入死亡状态；
- 外界如何观察一个对象是否仍然活着。

此前实现的信号槽模块可以回答：

- sender 与 receiver 如何建立连接；
- Connection 如何用 RAII 管理；
- receiver 死亡时如何自动断开连接；
- sender 先死亡时如何避免 Connection 访问失效状态。

两者融合后，新的核心生命周期可能是：

```text
Object 开始析构
→ ObjectPtr 失效
→ 自动断开该对象参与的信号连接
→ 发射 destroyed 信号
→ 解除父子关系
→ 级联销毁 children
```

因此，融合并不只是把两个头文件 include 到一起，而是在统一：

> 对象身份、层级所有权、非拥有观察和通信连接的生命周期。

这也是对象树学习完成后，最自然的下一阶段。

## 9. 总结

这次学习从一个非常朴素的问题开始：

```text
能不能让父对象在析构时自动删除 children？
```

但随着版本演进，问题逐渐变成：

```text
父子关系如何始终保持一致？
动态换父时谁负责维护双方？
怎样禁止对象树中出现环？
裸指针能否表达所有权？
unique_ptr 为什么会改变 API？
对象被正确释放后，外部观察指针怎么办？
```

最终得到的不是唯一正确的 Object 类，而是三层相互独立的设计：

```text
对象关系层
    parent / children

所有权层
    QObject 风格协议
    或 unique_ptr

生命周期观察层
    ObjectPtr / LifetimeToken
```

真正重要的收获，也不是某一段最终代码，而是下面这句话：

> 当一个指针出现在设计中时，首先应该问的不是“用裸指针还是智能指针”，而是“它表达的是所有权、观察，还是一次短期借用”。
