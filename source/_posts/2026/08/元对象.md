# 从类名到对象序列化：从零实现 C++ 元对象系统的 17 次演进

> 本文记录了一次受 Qt 元对象系统启发的 C++ 学习过程。
>
> 重点不是复刻 Qt，也不是为了模板而写模板，而是从一个只能报告类名的最小原型出发，在一次次真实问题的推动下，逐步得到运行时类型描述、对象工厂、属性访问、方法调用、元类型注册与对象序列化能力。

## 1. 为什么需要元对象系统？

C++ 本身是一门静态类型语言。编译器当然知道下面这些信息：

```cpp
Button button;
button.SetLength(3.0);
```

但这些信息主要服务于编译过程。程序运行以后，如果拿到的是字符串、配置文件或脚本数据：

```text
class = Button
property = M_Length
value = 3.0
method = F_SetPosition
```

普通 C++ 并不能直接回答：

- `Button` 是不是一个已知类？
- 它继承自哪个类？
- 能否仅根据类名创建对象？
- 它有哪些属性，属性分别是什么类型？
- 能否仅根据属性名读取或修改对象？
- 它有哪些方法，参数和返回值是什么类型？
- 能否仅根据方法名和一组运行时参数调用它？
- 能否在完全不知道具体派生类的地方序列化这个对象？

`typeid` 和 `dynamic_cast` 能解决其中一小部分问题，但它们不会自动列出类的属性、方法和构造方式，也不会替我们建立“名字到行为”的映射。

元对象系统的价值，就是在普通对象之外，再建立一层能够在运行时查询的数据描述：

```text
普通对象：保存一个实例此刻的数据
元对象：描述这一类对象拥有哪些结构和能力
```

Qt 的 `QMetaObject` 同样保存类名、父类、属性、方法、构造函数等元信息，并为属性系统、信号槽和运行时调用提供基础。Qt 主要借助 `moc` 在编译阶段生成这些重复代码；本项目则尝试只使用 ISO C++ 的模板、宏、成员指针、`std::function`、`std::any` 和 RTTI，亲手理解这层机制为什么存在。

参考资料：

- [Qt QMetaObject](https://doc.qt.io/qt-6/qmetaobject.html)
- [Qt Property System](https://doc.qt.io/qt-6/properties.html)
- [Qt QMetaType](https://doc.qt.io/qt-6/qmetatype.html)
- [Qt Meta-Object Compiler](https://doc.qt.io/qt-6/moc.html)

## 2. 最终形成的结构

先看最终版本中几个概念的关系：

```text
Object 实例
└── GetMetaObject()
    └── MetaObject：描述一个类
        ├── className / superClass
        ├── MetaProperty[]：描述可读写属性
        └── MetaMethod[]：描述可调用方法

MetaProperty / MetaMethod
└── MetaType：描述值的 C++ 类型和稳定名字
    └── Serializer / Deserializer
        └── SerializedValue：与具体 C++ 类型解耦的数据树

RegisterObject
└── className → MetaObject + 创建函数

SerializedObject
├── className
└── propertyName → typeName + SerializedValue
```

最终系统并不是突然设计出来的。上面的每一层，都来自前一版暴露出的不足。

---

## 3. Version 1：先让对象说出“我是谁”

第一版只保存两个信息：

```cpp
class MetaObject
{
private:
    std::string_view m_ClassName;
    const MetaObject* m_SuperClass;
};
```

每个类拥有一份静态 `MetaObject`，实例通过虚函数返回自己真正的元对象：

```cpp
virtual const MetaObject* GetMetaObject() const noexcept;
```

于是，即使外部只拿到 `Object*`，也可以在运行时得到真实派生类型：

```cpp
Object* object = new Button;
object->GetMetaObject()->ClassName(); // Button
```

沿着 `SuperClass()` 向上查找，还可以实现：

```cpp
buttonMetaObject->Inherits(widgetMetaObject);
```

### 3.1 这一版解决了什么？

它建立了元对象系统最小的核心：

```text
一个类
↔
一份静态、长期存在的类型描述
```

### 3.2 为什么不能停在这里？

仅仅知道类名和继承关系，仍然做不了多少事情。

外部必须先有一个对象，才能询问它是什么；系统还不能根据一个运行时类名创建对象。并且公开的静态成员变量使实现细节暴露在类接口中，也带来了初始化和访问形式上的疑问。

因此下一步自然变成：

> 如果我只有字符串 `"Button"`，能否创建一个真正的 Button？

---

## 4. Version 2：从类型信息走向运行时对象工厂

第二版将公开静态变量收束为静态函数：

```cpp
static const MetaObject* GetStaticMetaObject() noexcept
{
    static const MetaObject metaObject{"Button", Widget::GetStaticMetaObject()};
    return &metaObject;
}
```

函数局部静态对象把初始化和访问封装在一起，也保证了第一次调用时才初始化。

同时加入对象注册表：

```cpp
class ObjectRegister
{
    std::unordered_map<
        std::string,
        std::function<std::unique_ptr<Object>()>
    > m_ObjectsCreateFun;
};
```

注册时，模板仍然知道真实类型：

```cpp
registry.Register<Button>();
```

模板将 `std::make_unique<Button>()` 擦除为统一的创建函数。运行时只需要类名：

```cpp
std::unique_ptr<Object> object = registry.Create("Button");
```

### 4.1 什么叫“运行时创建”？

它并不是运行时凭空编译出一个程序中从未出现过的新类，而是：

```text
编译期：把 Button 的创建函数注册进表中
运行时：根据字符串选择并调用已经注册的创建函数
```

因此元对象系统不是编译器，而是一座桥：把运行时数据映射到编译期已经存在的 C++ 类型和行为。

### 4.2 新问题：类型不一定能创建

最初的工厂默认认为每个注册类型都能：

```cpp
std::make_unique<T>();
```

但一个类可能：

- 是抽象类；
- 没有默认构造函数；
- 只需要参与类型判断，却不允许直接创建。

如果注册表只保存创建函数，就无法表达“这个类型存在，但不能实例化”。

---

## 5. Version 3：区分“认识一个类型”和“能够创建它”

第三版把注册项改为：

```cpp
struct TypeEntry
{
    const MetaObject* m_Type = nullptr;
    std::function<std::unique_ptr<Object>()> m_CreateFun;
};
```

注册时通过编译期判断决定是否提供工厂：

```cpp
if constexpr (!std::is_abstract_v<T> &&
              std::is_default_constructible_v<T>)
{
    entry.m_CreateFun = [] {
        return std::make_unique<T>();
    };
}
```

这使系统能够表达两种不同事实：

```text
Object 已注册，所以它的 MetaObject 可以被查询
Object 是抽象类，所以它没有可调用的默认创建函数
```

### 5.1 这一版带来的设计认识

元信息和对象工厂有关联，但不是同一个概念：

```text
元信息回答“这是什么类型”
工厂回答“能否以及如何创建实例”
```

### 5.2 新问题：每个派生类都要写相同样板代码

每个类都需要重复：

```cpp
GetStaticMetaObject()
GetMetaObject() override
父类元对象连接
类名字符串
```

代码本身不难，但非常机械。只要有一个类漏写 `override`、写错父类或忘记返回静态对象，整条元信息继承链就会出错。

---

## 6. Version 4：用宏收束不可避免的样板代码

第四版引入：

```cpp
META_ROOT_OBJECT(Object)
META_OBJECT(Widget, Object)
META_OBJECT(Button, Widget)
```

宏负责生成静态元对象访问函数和虚函数覆盖。

### 6.1 为什么这里使用宏是合理的？

普通模板无法自动把当前类名 `Button` 变成字符串，也无法自动把一段成员函数声明“注入”类中。Qt 使用 `Q_OBJECT` 配合 `moc` 代码生成；当前项目不引入代码生成器，因此宏成为一个简单的替代方案。

宏并没有消除复杂性，只是把重复且容易写错的复杂性集中到一处。

### 6.2 编写宏时暴露的问题

根类型没有父类，如果试图统一展开为：

```cpp
Base::GetStaticMetaObject()
```

就可能生成类似：

```cpp
nullptr::GetStaticMetaObject();
```

因此根类和普通派生类需要两套宏。

此外，基类虚函数与派生类覆盖函数必须保持签名一致：返回类型、`const`、`noexcept` 都是函数类型的一部分；`virtual` 可以不重复书写，但 `override` 应保留，让编译器帮助检查。

### 6.3 宏之后的新问题

到这里，元对象仍然只描述“类”。真实的工具系统还会询问：

```text
这个类有哪些可配置数据？
我能否在不知道 Button 具体接口的情况下修改它？
```

这推动系统进入属性阶段。

---

## 7. Version 5：把成员变量映射为运行时属性

第五版加入 `MetaProperty`：

```cpp
class MetaProperty
{
public:
    using Getter = std::function<PropertyValue(const Object*)>;
    using Setter = std::function<bool(Object*, const PropertyValue&)>;

    PropertyValue Read(const Object*) const;
    bool Write(Object*, const PropertyValue&) const;
};
```

属性元数据不只保存名字，还保存真正能够读取和写入对象的函数。

`MakeMemberProperty` 接收成员指针：

```cpp
MakeMemberProperty<Widget, bool>(
    "visible",
    &Widget::m_Visible);
```

它把类型各不相同的成员访问，包装成统一接口：

```cpp
property.Read(object);
property.Write(object, value);
```

### 7.1 为什么这比直接访问成员变量有意义？

如果编译代码已经明确知道对象是 `Widget`，当然可以直接写：

```cpp
widget.m_Visible = false;
```

但配置面板、属性编辑器、脚本系统或反序列化器面对的通常只是：

```text
Object* + "visible" + 一个运行时值
```

调用者不再依赖具体类，才能写出一套服务于所有元对象类型的通用逻辑。

### 7.2 问题一：封装性怎么办？

成员指针必须在有权访问成员的位置取得。把它交给 `MetaProperty`，相当于类主动向元系统授予某项访问能力，而不是任何外部代码都突然可以访问私有成员。

不过，直接写成员仍然会绕过 setter 中可能存在的：

- 合法性检查；
- 数值裁剪；
- 缓存更新；
- 通知信号；
- 其他业务不变量。

### 7.3 问题二：属性类型被写死了

这一版使用：

```cpp
using PropertyValue =
    std::variant<int, bool, double, std::string>;
```

只要成员类型不在这个列表中，属性系统就无法承载它。此时还没有解决开放类型问题，但直接跳进复杂的泛型类型擦除会让学习跨度太大，因此先保留这个限制。

---

## 8. Version 6：属性不等于成员变量，而是一组访问语义

第六版加入 `MakeAccessorProperty`：

```cpp
MakeAccessorProperty<Button, std::string>(
    "text",
    &Button::Text,
    &Button::SetText);
```

表面上，`MetaProperty` 的 `Read/Write` 接口没有变化；内部却从直接操作成员指针变成了调用 getter 和 setter。

### 8.1 为什么必须演化？

属性是一种面向外部的稳定能力，不应该被限制为某个具体成员变量。

同一个属性可以：

- 直接对应一个成员；
- 通过 getter 动态计算；
- 通过 setter 校验输入；
- 只读而没有 setter；
- 在写入时触发其他行为。

因此：

```text
成员变量是存储方式
属性是访问协议
```

### 8.2 属性系统是否偏离了元对象主线？

恰恰相反。元对象本身只是一个容器，属性、方法、枚举等才是它要承载的内容。没有这些内容，元对象只能报告类名，很难产生实际价值。

这一版还出现了 `ApplyProperty`：调用者提供一张名字和值的表，就能将配置应用到任意对象。这第一次清晰展示了反射式属性访问相对于直接调用成员函数的意义。

### 8.3 下一步问题

属性只能表示“状态”。如果运行时配置或脚本要求对象执行动作，例如：

```text
调用 Button::Click()
```

系统还没有方法元数据。

---

## 9. Version 7：让无参成员函数成为元方法

第七版加入 `MetaMethod`，先只处理最简单的无参、无返回值成员函数：

```cpp
template<class Owner>
MetaMethod MakeMetaMethod(
    const std::string& name,
    void (Owner::*method)());
```

模板接收编译期成员函数指针，再把它包装为统一的运行时调用器：

```cpp
std::function<void(Object*)>
```

内部先通过 `dynamic_cast` 确认对象真实类型，再使用：

```cpp
std::invoke(method, owner);
```

### 9.1 为什么不能传 `const Object*`？

这一版调用的是非 `const` 成员函数。非 `const` 方法可能修改对象，因此不能通过 `const Owner*` 调用。统一入口必须接收 `Object*`。

这并不是 `std::invoke` 的限制，而是 C++ const 正确性的要求。

### 9.2 这一版仍然太弱

只有 `void Click()` 可以注册。只要方法需要一个参数，统一调用接口就无法表达。

---

## 10. Version 8：运行时调用开始携带参数

第八版让 `MetaMethod` 接收运行时参数列表，并先支持单参数成员函数：

```cpp
void Button::AddClick(int count);
```

运行时调用变为：

```cpp
method->Invoke(object, arguments);
```

调用前需要检查：

- 对象能否转换为正确的 `Owner`；
- 参数数量是否正确；
- 参数的实际类型是否匹配方法形参。

### 10.1 为什么不能为每种参数数量手写重载？

如果继续手写，很快就会出现：

```text
MakeMetaMethod0
MakeMetaMethod1
MakeMetaMethod2
MakeMetaMethod3
...
```

真正的问题不是“支持一个参数”，而是“支持任意数量的参数”。因此下一版必须进入可变参数模板。

---

## 11. Version 9：用参数包完成多参数调用

第九版把成员函数推广为：

```cpp
template<class Owner, class... Args>
MetaMethod MakeMetaMethod(
    const std::string& name,
    void (Owner::*method)(Args...));
```

运行时参数存放在容器中，而真正的成员函数需要独立实参。二者之间由 `std::index_sequence` 建桥：

```cpp
std::invoke(
    method,
    owner,
    std::get<StoredArgument<Args>>(arguments[Index])...);
```

这行代码同时做了三件事：

1. `Index` 逐个选出运行时参数；
2. `Args` 逐个决定每个参数应取出的类型；
3. 最后的 `...` 展开整段函数实参表达式。

### 11.1 为什么这里特别容易写错？

参数包展开的对象不是某个变量，而是一段模式：

```cpp
std::get<StoredArgument<Args>>(arguments[Index])
```

`...` 必须作用于包含参数包的完整模式。括号放错一层，就可能变成：

- 尝试展开容器本身；
- 把多个调用结果展开到 `std::invoke` 外面；
- 或把整个调用表达式重复多次。

编译错误往往发生在模板实例化深处，因此这一版真正学习的不只是元对象，还包括参数包、索引序列和模板错误的阅读方法。

### 11.2 新问题：调用成功却拿不到返回值

此时已经可以运行：

```cpp
void SetLength(double);
void GetInfo(std::string, int);
```

但所有方法仍被强制为 `void`。对于计算类方法，调用者需要知道返回值。

---

## 12. Version 10：统一 void 与非 void 返回

第十版加入：

```cpp
struct InvokeResult
{
    bool invokeSuccess{};
    std::optional<MetaValue> invokeResult;
};
```

模板通过 `if constexpr` 区分两类方法：

```cpp
if constexpr (std::is_void_v<R>)
{
    std::invoke(...);
    return {true, std::nullopt};
}
else
{
    R result = std::invoke(...);
    return {true, MetaValue{std::move(result)}};
}
```

### 12.1 为什么成功标记和返回值要分开？

`std::nullopt` 不能单独表示失败，因为一个合法的 `void` 方法本来就没有返回值。

因此必须区分：

```text
调用失败：invokeSuccess == false
void 方法成功：invokeSuccess == true，invokeResult 为空
非 void 方法成功：invokeSuccess == true，invokeResult 有值
```

### 12.2 新问题：同名方法无法只靠名字选择

C++ 支持重载：

```cpp
void SetLength(int);
void SetLength(double);
void GetLength();
void GetLength() const;
```

如果 `FindMethod()` 只比较名字，它无法判断应该选择哪一个。

---

## 13. Version 11：方法重载、参数签名与 const 成员函数

第十一版让 `MetaMethod` 除了名字和调用器，还保存：

```text
参数类型序列
返回类型
是否为 const 成员函数
```

查找方法时不再只比较名称：

```cpp
FindMethod(name, runtimeArguments, isConst);
```

系统会依次检查：

1. 名字是否相同；
2. 参数数量是否相同；
3. 每个参数类型是否相同；
4. `const` 属性是否相同。

### 13.1 注册重载函数为什么需要显式消歧？

表达式：

```cpp
&Button::SetLength
```

可能对应多个成员函数，编译器无法猜测希望注册哪一个，因此需要明确目标函数指针类型：

```cpp
static_cast<void (Button::*)(int)>(&Button::SetLength)
```

`QOverload`、显式 `static_cast` 和 lambda 的目标相同：给重载集合补充足够的类型信息。这不是元对象系统额外制造的问题，而是 C++ 重载函数取地址时本来就存在的歧义。

### 13.2 const 方法为什么需要独立模板重载？

下面两个指针类型不同：

```cpp
R (Owner::*)(Args...)
R (Owner::*)(Args...) const
```

不能只在函数体里加一个布尔值就让前者接收后者，因此 `MakeMetaMethod` 需要分别提供非 `const` 和 `const` 版本。

### 13.3 新问题：封闭的类型枚举再次成为瓶颈

为了匹配签名，这一版使用 `MetaTypeId` 枚举：

```cpp
Bool, Int, Double, String, Unknown
```

它和早期 `std::variant` 有同样的问题：每增加一个 `Point`，就必须修改中心枚举和多处分支。一个真正可扩展的元系统不能要求所有类型都预先写在核心代码中。

---

## 14. Version 12：从封闭类型列表走向开放元类型

第十二版引入 `MetaType`：

```cpp
class MetaType
{
private:
    std::type_index m_TypeId;
    std::string m_Name;
};
```

`MetaValue` 不再使用固定 `variant`，而是保存：

```cpp
std::any m_Value;
const MetaType* m_Type;
```

这样，自定义类型也可以直接进入元系统：

```cpp
MetaValue value{Point{3, 4}};
```

### 14.1 `std::any` 与 `MetaType` 分别负责什么？

```text
std::any：保存类型擦除后的真实值
MetaType：保存可比较、可查询的类型身份与元信息
```

只保存 `std::any`，上层每次都要依赖 `any.type()`；只保存 `MetaType`，又没有真实数据。两者组合后，属性和方法都可以使用统一的 `MetaValue`。

### 14.2 为什么需要类型退化？

同一个语义类型可能以不同形式出现：

```cpp
Point
const Point
Point&
const Point&
```

如果分别生成元类型，它们会被当成四种互不相同的运行时类型。通过：

```cpp
using StoredArgument = std::decay_t<T>;
```

系统把用于存储和值传递的类型规范化，使：

```cpp
GetMetaType<Point>() == GetMetaType<const Point&>();
```

### 14.3 为什么 `MetaValue` 构造函数需要约束？

通用转发构造函数可能把 `MetaValue` 自己也当成任意类型接收，抢占复制、移动构造，甚至造成递归包装。因此需要概念或 `requires` 排除 `MetaValue` 本身。

### 14.4 这一版的意义

从这里开始，属性类型、方法参数和返回值不再依赖核心库预先枚举。元系统第一次真正向用户自定义类型开放。

但 `MetaType` 目前仍主要用于比较。外部还不能完整查询一个方法的签名，也不能得到适合展示或持久化的稳定类型名。

---

## 15. Version 13：让元信息能够自我描述

第十三版补齐查询接口：

```cpp
method.ReturnType();
method.ParameterTypes();
method.ParameterType(index);
method.GetParameterCount();
method.IsConst();
method.Signature();
```

属性也暴露自己的类型：

```cpp
property.Type();
```

随后可以写出：

```cpp
DumpMetaObject(buttonMetaObject);
```

输出类、父类、属性和方法，例如：

```text
Button : Widget
properties:
    double M_Length
    Point M_Position
methods:
    void F_SetLength(int)
    void F_SetLength(double)
    Point F_GetPosition() const
```

### 15.1 为什么“能调用”之后还要“能描述”？

动态调用解决的是执行问题，自我描述解决的是工具发现问题。

属性编辑器、脚本绑定、调试面板和接口浏览器不能预先知道有哪些方法，它们必须先枚举元信息，再决定向用户展示什么、允许调用什么。

### 15.2 `typeid(T).name()` 为什么看起来很怪？

它返回的是实现定义字符串。不同编译器可能产生不同格式，复杂模板类型还会展开为很长的内部名字，例如完整的 `std::basic_string<...>`。

它适合调试，却不适合作为：

- 面向用户的显示名；
- 跨编译器协议；
- 序列化格式中的稳定类型标识。

### 15.3 元信息能否反序列化成新函数？

元信息可以根据名字找到并调用已经编译进程序的函数，却不能把一段描述自动变成任意新的本地 C++ 函数。后者需要解释器、JIT 或重新编译。

同样，`DumpMetaObject` 可以帮助崩溃报告记录对象类型和业务状态，但它不能代替调试器或操作系统提供的调用栈展开。

这些疑问推动下一版解决稳定类型身份问题。

---

## 16. Version 14：建立唯一、稳定、可命名的元类型注册表

第十四版加入中心注册表，两张表分别解决两个方向的查找：

```text
std::type_index → std::unique_ptr<MetaType>
类型名字        → const MetaType*
```

于是既可以写：

```cpp
GetMetaType<Point>();
```

也可以写：

```cpp
MetaTypeRegister::FindMetaType("Point");
```

### 16.1 为什么不能简单依赖模板里的静态对象？

模板会针对不同模板实参生成不同实例。如果类型规范化或辅助模板设计不严谨，看似相同的类型可能落入不同实例，得到不同的静态对象地址。

而后续系统把 `MetaType*` 当作类型身份比较：

```cpp
value.Type() == property.Type()
```

因此同一个规范化类型必须始终对应同一个对象。

中心哈希表负责唯一性，`unique_ptr` 则保证容器扩容时 `MetaType` 自身地址仍然稳定。

### 16.2 静态初始化顺序问题如何出现？

如果注册表本身是跨翻译单元的静态对象，另一个全局对象可能在它构造前调用注册函数，产生经典的静态初始化顺序问题。

解决办法是函数局部静态对象：

```cpp
static MetaTypeMap& GetMetaTypeMap()
{
    static MetaTypeMap map;
    return map;
}
```

它在第一次使用时初始化，也把底层容器隐藏在注册接口之后。

### 16.3 注册必须维护哪些不变量？

```text
同一 C++ 类型重复注册同一名字：幂等成功
同一 C++ 类型尝试改名：失败
不同 C++ 类型抢占同一名字：失败
注册前后取得的 MetaType 地址：保持不变
```

从这一版开始，类型名不再只是打印字符串，而成为运行时协议的一部分。

### 16.4 下一步问题

已经可以通过名字找到 `Point` 的 `MetaType`，但系统仍然不知道怎样把一个 `Point` 变成可以保存或传输的数据。

---

## 17. Version 15：把序列化能力放到元类型上

第十五版为 `MetaType` 增加：

```cpp
using Serializer =
    std::function<std::optional<std::string>(const std::any&)>;

using Deserializer =
    std::function<std::optional<std::any>(std::string_view)>;
```

注册类型时，同时注册它的编解码规则：

```cpp
RegisterMetaType<int>(
    "int",
    intSerializer,
    intDeserializer);
```

`MetaValue` 不需要知道当前保存的是 `int` 还是 `Point`：

```cpp
value.Serialize();
MetaValue::Deserialize(metaType, text);
```

真正的类型差异被收束到各自的 `MetaType` 编解码器中。

### 17.1 为什么每个自定义类型仍然需要注册规则？

C++ 没有内建的通用结构反射，系统无法自动知道：

```cpp
struct Point
{
    int x;
    int y;
};
```

究竟应该保存哪些成员、使用什么字段名、是否忽略某些缓存、旧版本字段怎样迁移。这些都是类型自身的语义，因此至少需要某种形式的描述：

- 手写编解码器；
- 字段注册；
- 宏；
- 代码生成；
- 或未来的静态反射。

复杂性不可能完全消失，只能被放到更合适、更集中的层次。

### 17.2 为什么直接把所有东西变成字符串会失控？

为了序列化一个简单的 `Point`，就必须自己处理：

```text
分隔符
括号
字段顺序
数字转换
缺失字段
错误格式
嵌套结构
```

如果每个类型都直接解析字符串，业务结构和文本格式被绑在一起。类型一多，代码会迅速变成一套不完整的 JSON/XML 解析器。

问题不在“序列化天然不该复杂”，而在于当前抽象层次过低：类型编解码器不应该同时负责业务数据映射和文本语法解析。

---

## 18. Version 16：引入与格式无关的通用数据层

第十六版用 `SerializedValue` 取代字符串：

```cpp
using Storage = std::variant<
    std::monostate,
    bool,
    int,
    double,
    std::string,
    Array,
    Object
>;
```

其中：

```cpp
using Array  = std::vector<SerializedValue>;
using Object = std::unordered_map<std::string, SerializedValue>;
```

`Point` 不再手动拼接 `"[3,4]"`，而是表达为结构化数据：

```cpp
SerializedValue::Object object;
object.emplace("x", point.x);
object.emplace("y", point.y);
```

### 18.1 这一层为什么重要？

它把原本混在一起的两个问题拆开了：

```text
C++ 对象 ↔ SerializedValue 数据树
SerializedValue 数据树 ↔ JSON / XML / 二进制 / 数据库
```

`Point` 只关心自己由 `x` 和 `y` 组成，不再关心 JSON 使用花括号还是二进制协议如何编码整数。

以后如果需要 JSON，只需要写一套：

```cpp
SerializedValue ToJson(...);
SerializedValue FromJson(...);
```

所有已经接入 `SerializedValue` 的类型都可以复用。

### 18.2 通用数据层不等于自动反射

内置标量类型可以用模板统一注册，因为它们和 `SerializedValue` 的标量分支基本一一对应。

自定义类型仍要描述字段映射，但不再重复解决字符串语法。复杂性从：

```text
每个类型 × 每种输出格式
```

降为：

```text
每个类型 → SerializedValue
每种格式 ↔ SerializedValue
```

这正是中间表示层带来的复用价值。

### 18.3 下一步问题

此时只能序列化单个 `MetaValue`。如果拿到的是 `Object*`，调用者仍然需要手工知道它有哪些属性以及该按什么顺序处理。

这正是元对象与序列化系统最终汇合的地方。

---

## 19. Version 17：对象级序列化完成闭环

第十七版定义对象快照：

```cpp
struct SerializedProperty
{
    std::string m_TypeName;
    SerializedValue m_Value;
};

struct SerializedObject
{
    std::string m_ClassName;
    std::unordered_map<std::string, SerializedProperty> m_Properties;
};
```

对象序列化流程是：

```text
Object*
→ GetMetaObject()
→ 沿继承链枚举 MetaProperty
→ Read() 得到 MetaValue
→ MetaType::Serialize() 得到 SerializedValue
→ 保存类名、属性名、类型名和值
```

反序列化流程则反向进行：

```text
SerializedObject.className
→ RegisterObject 创建具体派生对象
→ 根据属性名查找 MetaProperty
→ 根据类型名查找 MetaType
→ SerializedValue 还原 MetaValue
→ MetaProperty::Write() 写回对象
```

调用者完全不需要写：

```cpp
if (className == "Button")
{
    auto* button = ...;
    button->SetLength(...);
}
```

它只依赖统一元接口，因此同一套算法可以处理未来注册的其他类。

### 19.1 为什么需要遍历继承链？

`Button` 的元对象只保存自己声明的属性，而 `M_Visible` 属于 `Widget`。

对象序列化必须沿 `SuperClass()` 收集父类属性。当前实现先处理基类，再处理派生类；如果出现同名属性，派生类数据最终覆盖基类，符合派生类遮蔽的直觉。

### 19.2 为什么序列化数据必须拥有类型名？

早期 `SerializedProperty` 使用 `std::string_view`，它只是观察别处的字符串。快照一旦长期保存或跨模块传递，就可能悬空。

序列化结果本质上是独立数据，应使用 `std::string` 持有自己的类名、属性名和类型名。

### 19.3 为什么失败不能被静默跳过？

如果某个已知属性：

- 没有编解码器；
- 类型名和属性真实类型不一致；
- 数据格式错误；
- setter 拒绝写入；

却仍然返回一个对象，调用者会得到一个看似成功、实际只恢复了一部分的实例。

当前策略是：已知属性的类型、解码或写入失败，就让整个恢复返回 `nullptr`。由于正在构造的是局部 `unique_ptr`，失败对象不会暴露给外界。

对于未知属性，则可以选择忽略，为新旧数据格式兼容留下空间；缺失属性保留构造后的默认值。

### 19.4 为什么必须检查工厂返回值？

序列化数据可能来自外部，类名不一定已注册。下面的调用可能失败：

```cpp
auto object = registry.CreateObject(className);
```

在访问 `object->GetMetaObject()` 前必须检查空指针。元对象系统把大量编译期错误推迟到了运行期，因此每一个运行时边界都必须有明确的失败语义。

### 19.5 Version 17 的真正意义

这一版第一次把前面所有部件同时用起来：

```text
类名与继承关系      → 找到完整属性集合
对象工厂            → 根据数据创建派生对象
MetaProperty        → 通用读写属性
MetaMethod/MetaType → 统一描述行为和类型
MetaValue           → 携带类型擦除后的 C++ 值
SerializedValue     → 承接与格式无关的数据
```

元对象不再只是“打印一个类名”，而成为通用工具代码和具体业务类型之间的运行时桥梁。

## 20. 用 GoogleTest 为章节收尾

早期版本把 `assert` 集中写在 `test1()`～`test17()` 中，并通过全局静态对象自动运行。随着失败路径增多，这种方式逐渐暴露问题：

- Release 构建可能移除 `assert`；
- 测试中直接 `return` 会把失败伪装成成功；
- 一个大函数很难表达具体是哪条规则失败；
- 全局静态测试会再次引入初始化顺序问题；
- 很难单独运行某一种行为。

因此最终引入 GoogleTest，将测试按行为命名：

```cpp
TEST(ObjectSerializationTest, RoundTripsButton)
{
    // 创建对象、设置属性、序列化、恢复并核验
}
```

这里同样遵循“问题推动工具”的学习方式：不是为了学习测试框架而专门开一章，而是当简单 `assert` 已经无法清晰表达系统契约时，引入一个成熟且成本较低的测试工具。

实践中只需要先掌握：

```text
TEST       划分独立行为
ASSERT_*   前置条件失败后停止当前测试
EXPECT_*   记录失败并继续检查其他结果
CTest      统一发现和运行测试程序
```

例如，指针随后要被解引用时应使用：

```cpp
ASSERT_NE(object, nullptr);
```

普通结果比较则可以使用：

```cpp
EXPECT_EQ(snapshot.m_ClassName, "Button");
```

GoogleTest 不会替代对 C++ 生命周期的理解。例如，从临时 `MetaValue` 中调用 `GetIf<T>()` 后保存指针，临时对象销毁后仍然会悬空。测试代码同样必须先保存 `MetaValue`，再在它的生命周期内使用内部指针。

## 21. 贯穿 17 个版本的核心认识

### 21.1 元对象不是对象

```text
Object：某个实例的数据和状态
MetaObject：某一类对象共享的结构描述
```

因此一个类通常只需要一份静态元对象，而每个实例通过虚函数返回它。

### 21.2 运行时能力来自编译期注册

运行时创建和调用并不是凭空生成 C++ 类型或函数，而是：

```text
编译期保存类型安全的成员指针、工厂和编解码器
→ 擦除成统一接口
→ 运行时根据名字和类型选择
```

模板负责守住注册阶段的类型安全，类型擦除负责提供运行阶段的统一接口。

### 21.3 属性是协议，不是成员变量的别名

`MetaProperty` 的意义在于统一：

```cpp
Read(Object*)
Write(Object*, MetaValue)
```

它背后可以是成员指针，也可以是 getter/setter，甚至可以是计算属性。属性系统没有打破封装，而是让类显式决定向元系统开放什么能力。

### 21.4 方法身份不只包含名字

完整的方法身份至少包括：

```text
方法名
参数类型序列
const 属性
```

返回类型适合描述和验证，但 C++ 不能只靠返回类型重载，因此通常不用于区分同名重载。

### 21.5 类型擦除之后仍然需要类型身份

`std::function` 和 `std::any` 擦除了具体类型，让统一容器成为可能；但系统仍然需要 `MetaType` 检查参数、描述签名并找到编解码器。

```text
类型擦除解决“怎样放到同一个接口里”
元类型解决“擦除后怎样知道它原来是什么”
```

### 21.6 稳定名字已经是协议

一旦类名、属性名和类型名进入序列化数据，它们就不再只是调试文字。修改：

```text
Button → PushButton
M_Length → length
Point → Point2D
```

都可能破坏旧数据。因此真实项目还需要格式版本和迁移策略。

### 21.7 中间数据模型负责隔离复杂性

`SerializedValue` 最重要的作用不是模仿 JSON，而是把两类变化隔离开：

```text
C++ 类型如何映射为结构化数据
结构化数据如何编码为某种外部格式
```

如果没有中间层，每增加一种类型和一种格式，复杂度都会交叉增长。

### 21.8 失败语义也是 API 的一部分

元对象系统将很多原本由编译器发现的问题推迟到了运行期：

- 名字不存在；
- 类型不匹配；
- 参数数量错误；
- 类不能创建；
- 数据无法解码；
- 属性拒绝写入。

因此 `nullptr`、`bool`、`std::optional` 和 `InvokeResult` 不是附属细节，而是运行时系统必须认真设计的结果通道。

---

## 22. 当前系统明确没有解决什么

完成一个教学版系统，不等于无限扩张边界。当前实现有意没有继续处理：

- 带参数构造函数的动态选择；
- 枚举、类信息和更多元数据种类；
- 默认参数、可变参数函数、引用返回值和复杂限定符；
- 方法调用时的隐式类型转换；
- 容器类型的自动泛化；
- 指针成员、共享对象身份与循环对象图；
- 序列化格式版本和字段迁移；
- 线程安全的动态注册；
- 自动生成反射代码；
- 从文本生成新的本地 C++ 函数；
- 崩溃调用栈展开。

这些不是 V17 无法成立的缺陷，而是可以在真实需求出现时继续学习的新课题。

如果继续向 Qt 的方向扩展，比较自然的路线包括：

```text
MetaEnum
构造函数元信息
属性变更通知
元对象与信号槽签名统一
线程/事件循环中的延迟调用
代码生成或静态反射
```

---

## 23. 总结

这次学习最初的问题很小：

```text
能不能在运行时知道一个对象的类名？
```

但每得到一种能力，就会自然暴露下一层问题：

```text
知道类名
→ 能否按类名创建？

能够创建
→ 抽象类型怎么办？注册样板代码怎么办？

能够描述类
→ 能否按名字访问状态？

能够访问属性
→ 封装、自定义类型和通用配置怎么办？

能够调用方法
→ 参数、返回值、重载和 const 怎么办？

能够擦除类型
→ 如何保留可比较、可命名的类型身份？

能够注册类型
→ 如何把值持久化？

能够序列化单值
→ 如何避免每个类型都手写文本解析？

拥有结构化数据层
→ 如何自动处理整个对象及其继承属性？
```

最终得到的并不是一个完整的 Qt 替代品，而是一套足够小、又能够解释核心思想的运行时系统：

```text
MetaObject  描述类
MetaProperty 描述状态访问
MetaMethod  描述行为调用
MetaType    描述值类型与编解码能力
MetaValue   携带类型擦除后的运行时值
RegisterObject 建立名字到类型和工厂的映射
SerializedValue 隔离 C++ 对象与外部格式
```

最重要的收获不是最终某个模板函数，而是理解了元对象系统存在的原因：

> 当调用者在编译期不知道具体类型，却仍然需要发现、创建、读取、写入、调用或保存对象时，就需要一层稳定的运行时描述，把动态数据重新连接到已经编译好的 C++ 类型与行为。
